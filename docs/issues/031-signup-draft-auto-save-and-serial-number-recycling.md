# PRD: Signup Draft Auto-Save, Resumption & Serial Number Gap-Free Recycling

## Problem Statement

Users registering for the Global Agarwal Community Directory face two critical points of friction that degrade trust and corrupt directory sequence integrity:

1. **Catastrophic Data Loss on Drop-Off & Permanent Account Locking**:
   - The multi-step household registration form spans 4 comprehensive steps (Contact & Password -> Head of Household & Address -> Extended Family Members -> Security Verification & Consent).
   - If a user drops off at Step 2 or 3 (due to incoming calls, needing family members' details, finding photos, or browser closure), **all entered data is completely lost** because form state exists solely in volatile React component memory.
   - When the user returns to `/signup`, they must painfully re-type all family details from scratch.
   - If they previously submitted an application that was subsequently rejected by an admin, the system flags their email/phone as *"already registered"*, permanently locking them out with no mechanism to correct mistakes or resubmit.

2. **Permanent Serial Number Burn on Rejected Submissions**:
   - Community serial numbers (`HHN-000-000-XXX` for households and `MAFL-000-000-XXX` for members) are minted at registration time before moderation occurs.
   - When an application is rejected by an administrator, the serial number remains tied to the rejected row.
   - The sequence generator continues incrementing based on `MAX(serial_no)`, permanently burning numbers (e.g. if applicant `#169` is rejected, `#169` is lost forever and the next person gets `#170`).
   - Over time, spam and rejected submissions create irreversible gaps in the community's prestigious sequential registry.

## Solution

1. **Two-Tier Resilient Draft Engine & Intelligent Lifecycle Routing**:
   - **Local Auto-Save**: Automatically persist form state to `localStorage` with a 500ms debounce on every keystroke and step transition, excluding sensitive plaintext passwords.
   - **Server-Side Sync**: Persist `form_data JSONB` in PostgreSQL `registration_drafts` to ensure recovery across sessions.
   - **Smart Resumption Banner**: When navigating to `/signup`, detecting an unfinished draft displays a dismissible resume card: *"We found an unfinished application for [Head Name] at Step [X]. [Resume Application] or [Start Fresh]"*.
   - **Lifecycle-Aware Conflict Resolution**:
     - If `status = 'live'`: Prompt to log in.
     - If `status = 'pending_review'`: Provide direct status tracking link.
     - If `status = 'rejected'`: Display the rejection reason and provide an *"Update & Resubmit"* flow that repopulates their data and reopens their application for review.

2. **Gap-Free Serial Number Recycling Engine**:
   - When an admin rejects an application, the rejected household and member serial numbers are detached and reset to `NULL`.
   - The sequence generator (`generateNextMemberSerialNo` and `generateNextHouseholdNo`) incorporates gap detection: it queries for the lowest unused positive integer in the sequence before advancing `MAX + 1`.
   - If `#169` is released upon rejection, the very next approved or submitted registration automatically reclaims and inherits `#169`.

## Implementation Decisions

### Decision 1: Two-Tier Draft Architecture (Local + Server)
- The client maintains an active debounced draft in `localStorage` (`mafl_signup_draft_v1`).
- The database `registration_drafts` table is enhanced with a `form_data JSONB` column.
- Sibling fields and validations in `src/app/signup/page.tsx` remain strictly untouched; draft state is restored cleanly via React state setters upon confirmation.

### Decision 2: Plaintext Password Exclusion
- Form auto-save filters out `password` and `confirmPassword` from the saved draft payload. When resuming, users are prompted to enter their password again before final submission.

### Decision 3: Atomic Serial Number Gap-Filling Algorithm
The sequential numbering engine in PostgreSQL evaluates existing numbers and fills the lowest available gap within the registration advisory lock:

```sql
WITH existing_nums AS (
  SELECT NULLIF(regexp_replace(serial_no, '[^0-9]', '', 'g'), '')::bigint AS num
  FROM members
  WHERE serial_no LIKE 'MAFL-%'
),
bounds AS (
  SELECT 1 AS start_num, COALESCE(MAX(num), 0) + 1 AS max_num FROM existing_nums
),
gaps AS (
  SELECT s.n AS next_num
  FROM bounds, generate_series(bounds.start_num, bounds.max_num) s(n)
  WHERE NOT EXISTS (SELECT 1 FROM existing_nums e WHERE e.num = s.n)
  ORDER BY s.n ASC
  LIMIT 1
)
SELECT COALESCE((SELECT next_num FROM gaps), 1) AS next_serial;
```

### Decision 4: Rejection Lifecycle State Machine
- When rejected:
  1. `households.status = 'rejected'`
  2. `households.rejection_reason = reason`
  3. `households.serial_no = NULL`
  4. `members.serial_no = NULL`
- When resubmitted:
  1. Detect existing rejected household by `verified_contact`.
  2. Overwrite household fields with updated applicant payload.
  3. Replace member records.
  4. Reset `status = 'pending_review'`.
  5. Assign newly allocated serial number via gap-filler.
